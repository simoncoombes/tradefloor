REFERENCE

Atlas

Atlas runs your measurement in hundreds of slightly different markets and builds a table of what came out. You then ask the table which model settings your result actually depends on.

What It Does, Step by Step

  1. You name some model settings and a range for each. Say herding between 0 and 0.4.
  2. Atlas picks a few hundred combinations spread evenly across those ranges.
  3. It runs your own measurement function at each one. Your function decides what gets measured: a return, a drawdown you compute yourself, a fill rate, a realism statistic. Anything you can compute from a run.
  4. You get back a table with one row per combination: settings in, your numbers out.
  5. Everything else on this page is a question you ask that table. Which setting moved my number, what shape the effect had, and what trade-offs exist.

You measure once and can then ask as many questions as you like, since the table saves to a file.

How the Points Are Chosen

Evenly, using Latin hypercube sampling. Each range is cut into as many slices as there are points, and every slice gets exactly one point. That matters because a plain random sample leaves gaps and clumps that look like structure when you analyse them. Even coverage is also what makes a few thousand points useful across fifty settings at once. Sampling is seeded, so the same survey reproduces exactly.

Why Sampling Beats Searching

If you already know which settings matter, run a search. If you do not, a search fails expensively: the optimiser will happily wreck anything your objective does not measure, and you find out afterwards. Six calibration searches on this simulator were rejected in two days, each one revealing a trade the objective had made behind everyone’s back. Anything outside the objective is free for the optimiser to spend.

The other half of the problem was that nobody had measured how the settings move the outputs. Every search was a walk across a room no one had mapped, in a direction someone had guessed at. A survey maps it first. A Pareto front then puts every available trade side by side so a person picks, rather than an optimiser picking quietly.

The Methods

MethodQuestion it answers
sensitivity(output)Which parameters move this output, ranked by rank correlation. Curved monotone effects read correctly under ranks; a linear measure would bury them.
profile(param, output)What shape the effect has: monotone, saturating, an interior optimum, nothing. Each bin reports a median with its p10-p90 spread, never a bare mean, because every other parameter is varying inside a bin.
unidentified(outputs)Which parameters move nothing you named, and would waste a search's budget. The threshold tightens as the survey grows.
pareto(objectives)The non-dominated rows over several objectives at once. The method the module exists for.
attribution(a, b, output)Why B beats A, decomposed per changed parameter, with a noise scale beside each contribution.
explain(output) · report_front(...)The findings as prose that carries its own row counts, ranges and caveats inline.
confirm(candidate, baseline, ...)Whether a screening finding survives fresh seeds at full resolution. The check you always run before believing a survey result.

Reading Each Method's Output

sensitivity returns the correlations inside their provenance, so a number cannot shed its basis:

PYTHON 
s.sensitivity("return_pct")
# {"output": "return_pct",
#  "correlations": {"momentum_theta": 0.61, ...},  # sorted by |rho|
#  "rows_total": 500, "rows_used": 496, "rows_error": 3,
#  "rows_nonfinite": 1, "rows_outside_where": 0, "where": None}

s.sensitivity("return_pct", where={"garch_alpha": (0.06, 0.16)})
# the same question, restricted to a region of OTHER parameters

A magnitude here ranks influence over the sampled range. It is an ordering, and it says nothing about how much a unit change buys, so quote it as a rank and never as an elasticity.

profile is where decisions usually turn. An interior optimum says ship a tuned value; a monotone slide to the range edge says the mechanism is net harmful here. A rank correlation cannot tell those apart, and the binned marginal can:

PYTHON 
s.profile("momentum_theta", "return_pct", bins=12)
# each bin: {"low", "high", "n", "median", "p10", "p90"}
# log axes bin in log space, so bin counts stay near-uniform

pareto and report_front lay out every available trade at the same time:

PYTHON 
s.pareto({"return_pct": "max", "impact_bps": "min"})
print(s.report_front({"return_pct": "max", "impact_bps": "min"}))

attribution decomposes a difference between two vectors across the parameters that differ. It exists because of a specific failure: a candidate was described in a design document as delivering crisis severity "through correlation", which was right for one of its two parameters and backwards for the other. Every number involved was correct. The connecting sentence was invented.

PYTHON 
s.attribution(vector_a, vector_b, "return_pct", measured=(y_a, y_b))
# contributions per changed parameter, each with a noise scale;
# contributions inside 2x their noise land in "within_noise"

explain and the other prose renderers state the row counts, ranges and dropped-row tally they stand on, with their own caveats inline. A number invites scepticism and a sentence does not, so the sentence has to carry its own.

The Failure Modes

Ranges Are the Most Consequential Choice

axes_for defaults to a quarter to four times a preset's shipped value. That is a convention, and it has been wrong here: a 96-core search once concluded there was nothing to find because the best known value of crisis_blend_ramp (6.0, four point three times ship) sat just outside the default ceiling of 5.6. Override any range you have real information about. A parameter that ships at exactly 0.0 has no multiplicative box at all, and Atlas refuses to guess one, because guessing would silently decide what the map can see. Typo'd override names are refused too, since a typo would leave a default box silently in place.

Attribution Assumes Additivity

Each contribution is a main effect read off a marginal with every other parameter varying. Strong interactions break the assumption: on a purely multiplicative surface attribution can overstate a contribution several-fold, and an interaction between the changed parameters is attributed to neither. Pass measured= whenever you can. It supplies the true endpoint values, and the residual against the decomposition is the only signal that additivity failed. Without it, the summary says so explicitly rather than presenting an unchecked number.

Why You Re-measure

The refusal to reuse seeds exists because of a real loss. A candidate here was declared shippable on a 13% improvement. Measured on fresh seed blocks, the same gap read +0.1297 where it was found, then −0.0315, +0.0209 and +0.0233 elsewhere, reversing sign once. Discovery and validation had used the same thirty seeds, so re-measuring reproduced the same fluctuation exactly and reported it as confirmation. It tested reproducibility of the measurement, and said nothing about the effect. confirm therefore refuses overlapping seeds outright, refuses a survey with no seed record, and measures both vectors on the same fresh seeds so path noise cancels in the pair. In practice one block gives you a number and several tell you whether it is a property of the model or just of the paths.

What Atlas Cannot Tell You

  • A near-zero sensitivity is evidence of no monotone relationship over the sampled range at this resolution, never proof of inertness. A parameter that acts only in combination, or only past a threshold the sample never crossed, reads the same way. Ask the targeted question with where=.
  • A rank correlation ranks influence. It does not measure how much.
  • Failed runs are kept, not hidden. A vector whose measurement raises is recorded and skipped, because a parameter region that crashes the model is a fact about the model. Infrastructure failures cluster in expensive corners, so check where the drops are, not just how many.
