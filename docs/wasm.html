Running in the Browser

pretium compiles to WebAssembly, and the browser build produces bit-identical results to the native one. So you can put a market in a web page and every viewer gets the same market you did.

A Permalink That Reproduces Exactly

This is what the browser build is for. A URL carrying the seed, the roster and the parameters gives every viewer the same market, on any machine, in any browser. A worked example becomes something a reader can verify rather than take on trust, and a daily challenge becomes a fair contest because everyone is trading the identical tape.

That only works if the browser agrees with the reference implementation to the last bit, which is the measurement below.

Calling It From JavaScript

The build emits a JavaScript module. This is the parity check that ships in tools/wasm/check.mjs, which is also the shortest useful example:

JAVASCRIPT 
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
const pt = require(`${process.cwd()}/dist/wasm/pretium.js`);

pt.version();                                  // the crate version
pt.preset_names();                             // ["pt-v1", "pt-v2", ...]

// one fixed simulation, hashed:
// (instruments, universeSeed, simSeed, days, ticksPerStep, preset)
const digest = pt.priceDigest(12, 7, 3, 5, 65, 'pt-v3');

Both surfaces call one core function, engine::fixed_simulation_digest, so the check compares implementations of the engine rather than two harnesses that would then have to be kept in step themselves. The Python side of the same comparison is tests/test_wasm_parity.py.

Types come free if you want them: wasm-bindgen emits a .d.ts alongside the module, so TypeScript consumers get the signatures without anything extra. Nothing in the shipped tooling is TypeScript.

Building It

SHELL 
tools/wasm/build.sh

One command: it builds, runs wasm-bindgen, and verifies the digest. A build whose digest does not match fails there rather than in someone's browser.

Why This Is Possible Here

Most simulators cannot offer a deterministic browser build. Two things make it work here.

WebAssembly specifies IEEE-754 exactly for add, subtract, multiply, divide and square root, so the arithmetic is pinned by the spec rather than by the engine you happen to be running.

And this crate ships its own exp, log, sin and cos rather than calling the platform maths library, which is the usual reason a browser build disagrees with a native one. The same decision that buys cross-platform identity on the desktop is what buys it in the browser. See Under the Hood for the measurement behind that.

Where It Is Still Loose

Two caveats, stated rather than folded into a blanket determinism claim.

  • NaN payload bits are not specified by wasm. The digest refuses to hash a non-finite value, so if one appears you get a visible failure instead of a match that quietly means nothing.
  • Relaxed SIMD is non-deterministic by design. It is off by default and it has to stay off.

What wasm32-unknown-unknown Means

Readers ask, so: in <arch>-<vendor>-<os> both unknowns are literal. There is no filesystem, no sockets, no clock, no threads, no environment and no process. pretium is unaffected because its only dependencies are libm and sha2, neither of which wants any of that.

One practical note if you are integrating it: a Rust panic reaches JavaScript as RuntimeError: unreachable executed with no message attached, so install console_error_panic_hook before you spend an afternoon on a blank error.

One Implementation, Two Surfaces

The day loop lives in the core, so the browser and Python surfaces run the same code rather than two copies of it. Under the Hood has the design rule behind that, and why a binding that re-implements a modelling decision is a fork wearing the costume of glue code.
